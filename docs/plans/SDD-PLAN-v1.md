# 桂花图书馆实施计划（SDD/TDD）

- **版本**：v1.0
- **状态**：已废止（已被 v1.1 取代）
- **适用仓库**：`https://github.com/Xguihur/guihua-library.git`
- **执行门禁**：本版本不再作为执行依据；用户明确批准 v1.1 或后续版本前，专项执行工程师不得编码。

## 1. 背景、问题、目标与范围

### 1.1 背景与问题

当前仓库是空的 GitHub 仓库，没有现有应用、接口、数据模型、测试、CI 或部署配置。目标是渐进式建设一个个人书籍展示与管理系统：公开展示正在阅读和已读书籍；登录用户根据权限进入管理后台；后台管理用户、角色权限和书籍；书籍详情包含介绍、书评，并预留 GitHub 评论集成。

### 1.2 目标

1. 建立可持续扩展的 Vue 3 + NestJS + MongoDB monorepo 基线。
2. 先交付可访问的公开书籍图册和书籍详情，再交付登录、授权和后台管理。
3. 以书籍状态支持至少“正在读”和“已读完”两类公开展示。
4. 以可审计的契约和 TDD 测试保证前后端边界、授权边界和数据状态转换。
5. 将方案文档、接口契约、测试策略和验收记录纳入仓库版本管理。

### 1.3 非目标（v1 不做）

- 不实现复杂推荐、社交关系、私信、支付、订阅、全文搜索和多租户。
- 不在未确认供应商前锁定图片对象存储、部署平台或域名。
- 不自建评论系统；GitHub 评论只做经过确认的外部集成，不复制或篡改 GitHub 内容。
- 不在本计划中承诺 SSR、PWA、原生客户端或 SEO 指标；是否需要 SSR/预渲染需在发布目标确认后决定。
- 不把“动画效果好”解释为具体视觉方案；只规定可测试的可用性、降级和性能约束，视觉细节在 UI 设计阶段确认。

### 1.4 范围边界与阶段

- **阶段 0：工程基线**：monorepo、开发命令、环境变量校验、基础健康检查、契约包、CI 最小检查。
- **阶段 1：公开书库**：书籍数据模型、公开列表/详情 API、图册页、状态筛选、详情页、加载/空态/错误态。
- **阶段 2：认证与管理后台**：登录、会话、用户/角色/权限、路由保护、书籍 CRUD、审计字段。
- **阶段 3：评论与发布准备**：按选定的 GitHub 集成方案接入详情页，补充安全、可观测性、部署和回滚检查。

阶段之间以可运行、可验收的增量交付为界，不允许为“以后可能需要”提前引入未确认的复杂业务。

## 3. 术语、前置条件与不变量

### 3.1 术语

- **公开书库**：未登录访客可读取的书籍列表和详情。
- **书籍状态**：至少 `reading`（正在读）和 `finished`（已读完）；其他状态必须先进入契约评审。
- **权限**：不可再拆的操作标识，如 `book:read`、`book:write`、`user:read`、`user:write`、`role:read`、`role:write`。
- **角色**：权限集合；用户至少绑定一个角色，最终有效权限为角色权限集合的并集。
- **管理接口**：需要认证并执行权限检查的 `/api/admin/*` 接口。

### 3.2 前置条件

- Node.js、包管理器、MongoDB 的支持版本在阶段 0 通过 ADR 固化；本计划默认使用 pnpm workspace，NestJS/Mongoose 访问 MongoDB，Vue 3 + Vite。
- 开发环境提供独立 MongoDB 数据库和测试数据库；测试不得依赖生产数据。
- GitHub 评论集成必须先确认目标产品（例如 GitHub Discussions、giscus 或其他方案）及其公开性、权限和配置方式。

### 3.3 不变量

1. 未认证请求不能访问管理接口；缺少权限即使已认证也必须拒绝。
2. 公开 API 只返回公开书籍字段，不泄露用户凭据、角色内部信息、审计敏感字段或数据库内部实现细节。
3. 书籍状态只能取契约枚举；非法状态不能写入数据库。
4. 所有写操作校验输入、记录 `createdAt`/`updatedAt`，并返回稳定的错误结构。
5. 删除策略必须在契约中明确；在未确认前，管理后台不得提供不可恢复的物理删除按钮。
6. 密码（若采用本地账号）只存不可逆哈希；令牌和密钥只来自环境变量，不进入仓库和日志。
7. 前端权限控制只负责界面与路由体验，后端权限检查是唯一安全边界。
8. 动画不可阻断键盘操作、焦点可见性、文本阅读和 `prefers-reduced-motion` 用户的使用。

## 4. 对外契约（v1 提案）

契约以 `packages/contracts` 中的共享 schema/类型和 `docs/contracts/` 中的版本化说明为准；实现不得以控制器当前返回值替代契约。

### 4.1 API 基本约定

- Base URL：`/api`；JSON UTF-8；成功响应使用明确资源结构，不返回 Mongoose 文档对象。
- 列表默认分页，参数建议为 `page`（从 1 开始）和 `pageSize`（服务端限制最大值）；排序字段必须白名单化。
- 统一错误结构：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "可展示给客户端的稳定消息",
    "details": [{ "field": "status", "reason": "unsupported_value" }],
    "requestId": "string"
  }
}
```

`details` 可为空；生产响应不能包含堆栈、MongoDB 错误文本或密钥。

### 4.2 公开接口

- `GET /api/books?status=reading|finished&page=1&pageSize=20`
  - 200：`{ items: PublicBook[], page, pageSize, total }`
  - 400：分页或状态参数非法。
- `GET /api/books/:slug`
  - 200：`PublicBookDetail`，包含标题、作者、封面引用、状态、简介、书评及公开时间字段。
  - 404：书籍不存在或不公开；不得通过错误差异泄露隐藏资源。

`PublicBook` 的字段先保持最小：`id`、`slug`、`title`、`author`、`coverUrl`、`status`、`summary`、`reviewExcerpt`。完整书评、出版信息、标签等字段只有在确认内容模型后加入。

### 4.3 认证与授权接口提案

- `POST /api/auth/login`：输入账号标识和密码；成功返回短期访问凭证及会话信息，凭证传输/存储策略由安全 ADR 固化。
- `POST /api/auth/logout`：使当前会话失效；重复调用应幂等。
- `GET /api/auth/me`：返回当前用户的非敏感资料、角色和有效权限。
- `POST /api/auth/refresh`：仅在选择 refresh-session 方案后启用；禁止无条件长期有效令牌。

默认错误语义：输入格式错误 `VALIDATION_ERROR`；凭据不正确统一为 `INVALID_CREDENTIALS`；已认证但无权限为 `FORBIDDEN`；未认证为 `UNAUTHORIZED`。不得通过“用户不存在/密码错误”区分账号是否存在。

### 4.4 管理接口提案

- `GET/POST/PATCH /api/admin/books`：读取、创建、局部更新书籍；写入前校验 slug 唯一性和状态枚举。
- `GET/PATCH /api/admin/users`：查看和修改账号启用状态、角色绑定；不得返回密码哈希。
- `GET/POST/PATCH /api/admin/roles`：查看、创建、修改角色权限集合；权限标识必须来自服务端白名单。

每个管理接口定义所需权限；接口契约测试必须证明“有认证无权限”和“无认证”均不能绕过控制器、服务层或数据库层的边界。

### 4.5 兼容性、安全与性能约束

- API 版本以 `/api` 初版契约为基线；破坏性变更必须递增版本或提供迁移说明，不允许静默改字段语义。
- 公共读取接口不得依赖管理端 token；管理接口不得接受前端自报权限。
- 书籍列表首屏目标：在本地基准数据集下 API p95 小于 300 ms；正式生产阈值在部署环境确认后调整。
- 列表查询必须使用索引支持的过滤/排序；禁止无上限返回全表。
- 登录接口必须具备失败限流或等价的暴力破解缓解措施；具体阈值在安全 ADR 中确定。

## 5. 设计方案与关键决策

### 5.1 Monorepo

建议目录：

```text
apps/
  web/                 # Vue 3 + Vite 公共站点与管理路由
  api/                 # NestJS HTTP API
packages/
  contracts/           # DTO/schema、枚举、错误码、前后端共享类型
  config/              # 可复用 TypeScript/ESLint/测试配置（确有重复后再抽取）
docs/
  plans/               # 版本化实施计划
  contracts/           # API/数据契约
  adr/                 # 关键架构决策记录
```

阶段 0 使用 pnpm workspace；只有出现真实重复或共享契约需求时才新增 package，避免空壳抽象。前后端通过 HTTP 契约解耦，`apps/web` 不直接依赖 NestJS 内部模块或 MongoDB 模型。

### 5.2 数据模型

初版集合提案：`books`、`users`、`roles`、`sessions`（若采用服务端会话/refresh 会话）。书籍使用稳定 `id` 和唯一 `slug`，状态为枚举，公开性由明确字段控制。用户、角色和会话字段按最小权限原则建模；密码哈希、会话密钥等字段不得序列化到公开 DTO。

暂不引入多态内容模型、全文搜索索引和事件总线。确有需求时以 ADR 和迁移脚本进入后续版本。

### 5.3 认证、授权与前端路由

后端采用认证 guard + 权限 guard；权限检查集中于服务端策略，避免只在控制器装饰器中分散复制。前端通过 `/api/auth/me` 获取当前能力，按权限显示后台入口，并对受保护路由展示未登录/无权限页面；前端隐藏按钮不视为授权。

密码登录、第三方登录、管理员首账号创建尚未由需求确定。本计划默认先实现本地账号的最小闭环，但在编码前必须确认：首个管理员如何安全创建、是否开放注册、是否需要邮箱验证和找回密码。

### 5.4 评论集成

评论不是阶段 1 的阻塞项。阶段 3 先产出适配器边界：书籍详情提供稳定的评论标识；集成组件只接收已批准的公开配置；GitHub 侧权限、内容审核、删除和隐私由选定产品负责。若选用第三方嵌入，必须有 CSP、脚本来源、降级占位和隐私说明；不在 API 中伪造评论数据。

### 5.5 动画与可访问性

组件层只允许不影响内容可达性的入场/悬停动画；统一支持减少动画、键盘焦点、语义标题、图片替代文本和移动端布局。验收以可观察行为为准，不把主观“好看”写成不可执行的代码标准。

### 5.6 关键取舍

- 选择共享契约而非前后端各自定义 DTO：减少字段漂移，代价是契约包需要版本控制。
- 选择 NestJS/Mongoose 而不是直接在控制器中操作 MongoDB：保持模块边界和校验可测试，代价是增加 schema/DTO 层。
- 先做公开读取再做后台写入：用户可尽早看到价值，且降低认证和内容录入同时变更的风险。
- 先做可配置评论适配器而非绑定某个 GitHub 产品：避免未确认供应商造成返工，代价是阶段 3 前需完成产品决策。

## 6. 依赖排序的实施步骤

每一步遵循“先写失败测试/契约，再实现，再运行验证”；执行 Agent 不得跳过失败测试或以快照代替行为断言。

1. **阶段 0.1 计划与 ADR 落地**：新增 `docs/adr/0001-stack-and-workspace.md`、`docs/contracts/errors.md`；固化 Node/pnpm/MongoDB 支持版本、包管理命令和环境变量清单。无业务实现。
2. **阶段 0.2 Monorepo 基线**：新增根 `package.json`、`pnpm-workspace.yaml`、TypeScript/ESLint/测试配置、`apps/web`、`apps/api`、`packages/contracts`。先验证安装、类型检查、单元测试和健康检查命令。
3. **阶段 1.1 数据与公开契约**：在 `packages/contracts` 先写书籍状态、公开 DTO、分页和错误 schema 的失败契约测试；在 `apps/api` 增加 books 模块、Mongo schema、索引和 repository/service；实现公开 GET 接口。
4. **阶段 1.2 公共站点**：在 `apps/web/src` 新增书库列表、状态筛选、详情路由和 API client；先写组件/路由行为测试，再实现加载、空态、404、错误态、键盘操作和减少动画。
5. **阶段 1.3 阶段 1 验收**：使用测试数据库运行 API 契约/集成测试，启动前后端做手工 smoke；确认访客可浏览 reading/finished，不能写入管理资源。
6. **阶段 2.1 认证契约与安全 ADR**：先写 login/logout/me/权限矩阵失败测试，确认管理员初始化、注册策略、令牌/会话方案和限流阈值；在 `apps/api/src/auth`、`users`、`roles` 实现。
7. **阶段 2.2 管理接口**：先写未认证、无权限、有效权限、非法输入、slug 冲突和状态转换测试；再实现 `apps/api/src/admin` 书籍/用户/角色模块。为写入增加审计字段和幂等/并发处理策略。
8. **阶段 2.3 管理前端**：在 `apps/web/src/features/admin` 实现登录、能力加载、路由保护、书籍/用户/角色页面；测试页面行为不依赖“隐藏按钮”模拟授权。
9. **阶段 3.1 评论适配器**：在 `packages/contracts` 固化评论配置边界和详情页锚点；在 web 侧接入批准的 GitHub 方案，验证脚本策略、隐私文案、禁用/加载失败降级。
10. **阶段 3.2 发布准备**：补充 Docker/部署配置（目标确认后）、迁移/备份/恢复说明、日志脱敏、健康检查、CI、发布和回滚清单。不得把部署成功假设为本地测试通过。

过渡或旧实现删除项：当前无旧实现、兼容别名或迁移调用方；阶段 0 后若出现临时脚手架，必须在对应阶段验收前删除，不保留空壳 endpoint、mock fallback 或 TODO 实现。

## 7. TDD 测试矩阵

| 领域 | 先写的失败测试 | 正常路径 | 边界/错误/回归 | 通过标准 |
|---|---|---|---|---|
| 工程基线 | 空环境变量、健康检查不可用时命令失败 | 安装、类型检查、测试、启动成功 | 测试配置不读取生产数据库 | 根命令可重复执行，失败有明确退出码 |
| 书籍契约 | 缺少 title/status、非法 status、错误分页被拒绝 | 合法 DTO 解析为稳定结构 | 长文本、空摘要、重复 slug、未知字段 | schema、API 响应和前端类型一致 |
| 公开 API | 未实现路由/仓储时测试失败 | reading/finished 筛选、分页、详情 | 空结果、404、DB 错误不泄露内部信息 | API 契约测试全通过，列表有上限和索引 |
| 公开 UI | API pending/error/empty 时界面断言失败 | 卡片、筛选、详情和返回导航 | 键盘焦点、移动宽度、减少动画、封面失败 | 可访问行为和状态页面可观察且稳定 |
| 认证 | 未认证访问 admin、错误凭据、会话失效失败 | login、me、logout 闭环 | 重复 logout、账号禁用、令牌过期、枚举泄露 | 错误码稳定，敏感字段不出响应/日志 |
| RBAC | 已登录但无权限调用写接口失败 | 角色权限允许对应操作 | 修改角色即时生效、权限白名单、越权路径 | 后端 guard/service 测试证明不可绕过 |
| 管理书籍 | 非法状态/重复 slug/缺权限失败 | 创建、读取、局部更新 | 并发更新、未知字段、审计字段 | 数据约束与 API 行为一致 |
| 管理用户/角色 | 越权改管理员、未知权限失败 | 绑定角色、启停账号、角色 CRUD | 最后管理员保护策略（确认后测试） | 权限矩阵逐项通过 |
| 评论适配器 | 未配置/脚本失败的降级测试失败 | 批准供应商正确渲染 | CSP/隐私/禁用配置、第三方不可用 | 无评论服务时详情仍可用 |
| 回归/契约 | OpenAPI/schema 与实现不一致时失败 | 前后端共享契约通过 | 破坏性字段变更要求版本/迁移说明 | CI 阻止契约漂移和类型错误 |

永久测试只断言消费者可观察行为、边界、状态转移和安全不变量；不测试“复制了某个对象”“按钮数量”“源码文本”或单纯“不抛异常”。

## 8. 验收标准

### 8.1 阶段 0

- 从干净工作树执行文档规定的安装、类型检查、测试和启动命令，均有确定结果。
- `apps/api` 健康检查能区分服务可用与数据库不可用；敏感配置缺失时启动失败且消息可操作。
- `packages/contracts` 可被 web 和 api 引用，至少包含错误结构、书籍状态和分页约束。

### 8.2 阶段 1

- 未登录访客能查看 reading 与 finished 书籍卡片，能进入详情；无数据、加载失败、404 均有明确界面。
- API 只返回公开字段；非法分页/状态被拒绝；公开读取不会写数据库。
- 键盘用户、移动端和减少动画设置下仍能完成列表到详情的主要流程。

### 8.3 阶段 2

- 有效账号能登录、查看自身权限并按权限看到后台入口；退出后受保护页面和管理 API 均不可访问。
- 无权限用户即使直接构造 HTTP 请求也不能读写对应资源。
- 授权管理员能依据契约管理书籍、用户角色；非法输入、重复 slug、禁用账号和错误凭据具有稳定错误语义。
- 密码、令牌、哈希和数据库内部错误不会出现在响应、前端存储（按批准的会话方案）或日志中。

### 8.4 阶段 3/发布

- 评论集成按批准产品工作；未配置、被禁用或第三方失败时书籍详情仍可用。
- CI 执行契约、单元、集成、前端行为、类型检查和 lint；发布前完成备份、迁移、回滚和密钥检查。
- 运行一次真实的本地端到端 smoke：访客浏览 → 登录 → 授权管理书籍 → 退出 → 越权请求被拒绝。

## 9. 风险、回滚与发布检查

### 9.1 风险

- 空仓库无法证明现有约束；错误的早期架构会扩大后续迁移成本。
- 本地账号、管理员初始化和权限删除规则未确认，可能造成不可恢复的管理锁死。
- GitHub 评论产品、第三方脚本和隐私策略未确认，可能影响安全审查和发布。
- 图片存储、部署、备份未确认，可能使“可用展示”无法直接上线。
- MongoDB schema 演进无强约束；必须用显式迁移/回填脚本和备份验证控制风险。

### 9.2 回滚策略

- 每阶段使用可独立运行的提交；接口破坏性变更前先增加兼容读取或版本化契约。
- 数据库变更先备份、在测试库回放，迁移脚本必须可重复执行或明确不可逆步骤。
- 发布失败优先回滚应用版本；仅在已验证兼容时回滚 schema。评论集成可通过配置关闭，不得阻断书籍详情。
- 禁止使用无审计的生产数据删除作为回滚手段。

### 9.3 发布检查

契约版本、环境变量、密钥来源、CORS/CSP、限流、日志脱敏、索引、备份恢复、健康检查、监控告警、迁移记录、回滚命令和真实 smoke 均必须有证据；未验证项不得标记完成。

## 10. 未决问题与最小澄清

以下问题不阻塞计划审核，但会阻塞对应实现阶段；若用户未指定，执行前采用计划中的默认值并在 ADR 中记录，或暂停该阶段而不擅自补充业务规则：

1. **账号**：是否只允许管理员预置账号，还是开放注册？首个管理员由 CLI 一次性创建、环境变量初始化，还是人工导入？是否需要邮箱验证/找回密码？
2. **会话**：是否接受本地账号密码？若接受，采用 httpOnly refresh cookie + 短期 access token，还是服务端会话？
3. **书籍**：除 title/author/cover/status/summary/review 外，是否需要 ISBN、出版信息、标签、阅读日期、评分、原文摘录？是否允许草稿/下架状态？
4. **评论**：选择 giscus、GitHub Discussions、utterances 还是其他方案？评论是否公开、是否需要 GitHub 登录、谁负责审核？
5. **部署与资源**：目标部署平台、域名、MongoDB 托管方式、封面存储和备份保留周期是什么？
6. **渲染与视觉**：是否需要 SSR/预渲染和 SEO；动画风格、品牌色、移动端优先断点由谁确认？
